2.2 Flusso dei Dati

Utente -> Frontend (Angular) -> HTTP REST (JSON) -> Backend (Spring Boot) ->
  PostgreSQL (dati applicativi) + Keycloak (autenticazione, gestione password)

Schema flusso login:
  POST /api/v1/auth/keycloak-login { username, password }
    -> Verifica status utente nel DB locale (ACTIVE/PENDING/ANNULLED/SUSPENDED)
    -> Chiamata Keycloak /protocol/openid-connect/token (grant_type=password)
    -> Parsing JWT, estrazione keycloakId dal subject
    -> Sync/creazione utente locale se necessario
    -> Restituzione JWT + dati utente al frontend

Schema flusso richieste autenticate:
  Frontend -> [auth.interceptor: aggiunge header Authorization: Bearer <JWT>]
    -> Backend SecurityConfig: oauth2ResourceServer(JwtDecoder)
    -> JwtAuthenticationConverter -> AppRoleConverter (ruoli da realm_access)
    -> Filtro JwtPasswordChangeFilter (verifica password_changed_at)

2.3 Gestione Stato Globale Frontend

Lo stato è gestito tramite:
  - localStorage: token JWT, dati utente (LoginResponseDto), flag pin_verified
  - Servizi Angular (injectable) condivisi: AuthService, ToastService
  - Signal API (@angular/core signals): utilizzo massiccio di signal() e computed()
    nei componenti per reattività locale
  - Non vengono utilizzati store globali (NgRx, Akita, etc.)

2.4 Autenticazione e Autorizzazione

Autenticazione:
  - Keycloak è l'identity provider (OpenID Connect)
  - Login via password grant_type (client 'bank-backend')
  - JWT firmato da Keycloak, validato via JwtDecoder (issuer-uri)
  - Ruoli mappati da realm_access.roles a GrantedAuthority

Ruoli Utente:
  - C (Cliente/Customer): gestione conti, transazioni, carte, beneficiari
  - D (Dipendente/Employee): validazione registrazioni, gestione conti/carte/limiti
  - A (Admin): gestione impiegati, clienti, conti, transazioni, audit log

Middleware/Protezione Rotte:
  - Backend: @PreAuthorize("hasRole('C')") / hasRole('D') / hasRole('A')
  - Frontend: roleGuard('C') etc. + limitsSetupGuard, pinSetupPageGuard

4.1 Modulo Auth

--- POST /api/v1/auth/register ---
  Controller: AuthController.register()
  Scopo: Registrazione nuovo utente cliente
  Accesso: Pubblico
  Richiesta Body:
    {
      "firstName": "Mario",
      "lastName": "Rossi",
      "email": "mario.rossi@email.com",
      "password": "Password123!",
      "birthDate": "1990-01-01",
      "profession": "Impiegato",
      "gender": "M",
      "fiscalCode": "RSSMRA90A01H501U",
      "phone": "+391234567890",
      "residence": "Via Roma 1, Milano",
      "birthPlace": "Roma",
      "birthProvince": "RM"
    }
  Servizio: RegistrationService.register()
    -> createPendingUser():
       1. Verifica email non già registrata (findByEmail)
       2. Verifica username (email) non già usato (findByUsername)
       3. Cerca ruolo "C" (Cliente) e stato "PENDING"
       4. Crea utente su Keycloak via keycloakAdminService.createUser()
          (userBody: username=email, email=email, password, enabled=false)
          -> Assegna ruolo realm "C" in Keycloak
          -> Restituisce keycloakId
       5. Salva utente locale con stato PENDING, keycloakId
       6. Crea conto iniziale INACTIVE via AccountService.createInitialAccountForUser()
    -> Salva utente
  Risposta: 200 OK con UserResponseDto
    {
      "id": 1,
      "username": "mario.rossi@email.com",
      "firstName": "Mario",
      "lastName": "Rossi",
      "email": "mario.rossi@email.com",
      "birthDate": "1990-01-01",
      "statusId": 1,
      "profession": "Impiegato",
      "gender": "M",
      "fiscalCode": "RSSMRA90A01H501U",
      "phone": "+391234567890",
      "residence": "Via Roma 1, Milano",
      "profilePictureUrl": null
    }
  Errori:
    - 400 EMAIL_ALREADY_REGISTERED: email già presente
    - 400 USERNAME_ALREADY_REGISTERED: username (email) già presente
    - 400 KEYCLOAK_USER_EXISTS: conflitto su Keycloak
    - 400 KEYCLOAK_CREATION_FAILED: errore creazione Keycloak
    - 400 ACCOUNT_CREATION_FAILED: errore creazione conto iniziale

--- POST /api/v1/auth/keycloak-login ---
  Controller: AuthController.keycloakLogin()
  Scopo: Login con username/email e password via Keycloak
  Accesso: Pubblico
  Richiesta Body:
    {
      "username": "mario.rossi@email.com",
      "password": "Password123!"
    }
  Logica:
    1. Normalizza username in lowercase
    2. Cerca utente locale (findByUsername). Se trovato e NON ACTIVE:
       - PENDING -> "ACCOUNT_PENDING"
       - ANNULLED -> "ACCOUNT_ANNULLED"
       - SUSPENDED -> "ACCOUNT_SUSPENDED"
       - default -> "ACCOUNT_UNAVAILABLE"
    3. Chiama Keycloak tokenLogin (password grant, client bank-backend)
    4. Se Keycloak fallisce -> INVALID_CREDENTIALS
    5. Parsing JWT -> keycloakId (subject claim)
    6. Se user locale non trovato -> syncKeycloakUserToDb() (crea utente ACTIVE)
    7. Se keycloakID diverso/null -> aggiorna utente locale
    8. Restituisce LoginResponseDto con JWT
  Risposta: 200 OK
    {
      "token": "eyJhbGciOiJSUzI1NiIs...",
      "role": "C",
      "userId": 1,
      "firstName": "Mario",
      "lastName": "Rossi",
      "email": "mario.rossi@email.com",
      "limitsSetupComplete": false,
      "pinSetupComplete": false,
      "profilePictureUrl": null
    }
  Errori:
    - 400 ACCOUNT_PENDING/ACCOUNT_ANNULLED/ACCOUNT_SUSPENDED/ACCOUNT_UNAVAILABLE
    - 400 INVALID_CREDENTIALS
    - 400 INVALID_TOKEN
    - 400 KEYCLOAK_ERROR

5. LOGICHE DI BUSINESS PRINCIPALI
================================================================================

5.1 Flusso Registrazione, Approvazione, Rifiuto e Riapertura

1. REGISTRAZIONE INIZIALE
   Utente -> POST /api/v1/auth/register
   -> Keycloak: crea utente DISABILITATO (enabled=false) con ruolo "C"
   -> DB: utente stato PENDING, keycloacId salvato
   -> DB: conto INACTIVE creato
   -> Attesa validazione impiegato

2. APPROVAZIONE (prima volta)
   Impiegato -> PUT .../registrations/{userId}/validate
   -> Keycloak: setUserEnabled(true)
   -> DB: utente -> ACTIVE
   -> DB: conto -> ACTIVE
   -> DB: carta DEBIT emessa (ACTIVE)
   -> Notifica utente

3. RIFIUTO
   Impiegato -> PUT .../registrations/{userId}/reject
   -> Keycloak: setUserEnabled(false) (disabilita, non cancella)
      NOTA: fix applicato - in precedenza deleteUser() + setKeycloakId(null)
      causava il bug di login dopo riapertura
   -> DB: utente -> ANNULLED
   -> keycloakId preservato
   -> Notifica rifiuto

4. RIAPERTURA
   Impiegato -> PUT .../registrations/{userId}/reopen
   -> DB: utente -> PENDING
   -> keycloakId ancora presente

5. APPROVAZIONE DOPO RIAPERTURA
   Impiegato -> PUT .../registrations/{userId}/validate
   -> keycloakId != null -> setUserEnabled(true) (riattiva Keycloak)
   -> DB: utente -> ACTIVE, conto -> ACTIVE
   -> Login funziona (password Keycloak preservata)

6. ELIMINAZIONE DEFINITIVA
   Impiegato -> DELETE .../users/{userId}
   -> Solo se stato ANNULLED
   -> Cancella tutti i dati associati (carte, limiti, transazioni, etc.)
   -> Keycloak: deleteUser(keycloakId)
   -> DB: elimina record utente

5.2 Flusso Transazioni

DEPOSITO (cliente):
  -> Verifica proprietà conto
  -> Aggiunge importo al balance
  -> Salva transazione COMPLETED (type=DEPOSIT)
  -> Notifica

PRELIEVO (cliente):
  -> Verifica importo >= 10 EUR
  -> Verifica proprietà conto
  -> accountLimitService.validateWithdrawal(account, amount)
     -> Verifica limite ATM_WITHDRAWAL (se configurato)
  -> Sottrae importo dal balance (se fondi sufficienti)
  -> Salva transazione COMPLETED (type=WITHDRAWAL)
  -> Notifica

BONIFICO ISTANTANEO (cliente):
  -> Verifica importo >= 1 EUR
  -> Se stesso proprietario o isInstant=true
  -> accountLimitService.validateTransfer(source, amount, isInstant)
     -> Verifica: SINGLE_TRANSFER, DAILY_TRANSFER (cumulativo giornaliero),
        INSTANT_TRANSFER_SINGLE, MONTHLY_TRANSFER (cumulativo mensile)
     -> Somma importi delle transazioni COMPLETED del giorno/mese in corso
     -> Se somma + nuovo importo > limite -> LIMIT_EXCEEDED
  -> Sottrae da source balance, aggiunge a destination balance (atomico)
  -> Salva transazione COMPLETED (type=INSTANT_TRANSFER o TRANSFER)
  -> Notifica mittente e destinatario

BONIFICO PROGRAMMATO (cliente):
  -> Stesse validazioni (limiti verificati alla creazione, non all'esecuzione)
  -> Data programmata: domani <= data <= oggi + 30 giorni
  -> Salva transazione PENDING (type=TRANSFER)
  -> ScheduledTransferProcessor (cron minuto) esegue alla data prevista:
     -> Verifica conto sorgente attivo e fondi sufficienti
     -> Esegue trasferimento (atomico)
     -> COMPLETED o FAILED
  -> Notifica

ANNULLAMENTO TRANSAZIONE (cliente):
  -> Solo transazioni PENDING (programmate)
  -> Setta stato CANCELLED

AGGIORNAMENTO ATOMICO SALDI:
  TransferFunds() in TransactionService:
    -> Tutte le operazioni sono @Transactional
    -> source.setBalance(source.getBalance().subtract(amount))
    -> destination.setBalance(destination.getBalance().add(amount))
    -> accountRepository.save(source) e save(destination)
    -> transactionRepository.save(transaction)
    -> Ottimistic locking via @Version su Account garantisce consistenza

5.3 Regole e Vincoli Finanziari

  - Saldo non può andare negativo (controllo INSUFFICIENT_FUNDS)
  - Prelievo minimo: 10 EUR
  - Bonifico minimo: 1 EUR
  - Max 3 conti non chiusi per utente
  - Chiusura conto: solo se saldo ZERO, non è ultimo attivo
  - Apertura conto aggiuntivo: solo se nessun conto INACTIVE pending
  - Limiti di transazione: configurabili per account per tipo limite
  - Tipi limite: DAILY_TRANSFER, SINGLE_TRANSFER, INSTANT_TRANSFER_SINGLE,
    MONTHLY_TRANSFER, ATM_WITHDRAWAL, POS_SPENDING
  - Change policy limiti:
    USER_FULL: utente può alzare/abbassare
    USER_LOWER_ONLY: utente solo abbassare
    BANK_ONLY: solo impiegato/admin può modificare

5.4 SecurityUtil

  Metodo assertOwnership(account, userId):
    -> Verifica che l'account appartenga all'utente con userId
    -> Se non corrisponde -> FORBIDDEN

5.5 Servizio Notifiche

  NotificationService.send(userId, type, message, messageKey, messageParams):
    -> Crea record Notification
    -> Se messageKey inizia con "NOTIF_" e messageParams != null ->
       NOTIF_ prefisso indica notifica "importante"
    -> Salva con timestamp Europe/Rome

5.6 Servizio Audit

  AuditLogService.log(entityType, entityId, action, performedBy, details):
    -> Registra evento con timestamp
    -> Opzionale performedByUserId per tracciamento

8. INTEGRAZIONE PHOTON E SERVIZI GEO/COMUNI
================================================================================

8.1 Servizio Comuni Italiani (Backend)

File: comuni/service/ComuniService.java
  Metodo init() (@PostConstruct):
    - Carica file comuni.json dal classpath (ClassPathResource)
    - Usa Jackson ObjectMapper per deserializzare in List<Map<String, Object>>
    - Estrae per ogni record: "nome" (nome comune), "sigla" (provincia),
      "codiceCatastale" (codice catastale di 4 caratteri)
    - Popola due liste parallele: allComuni (List<ComuneDto>) e
      allComuniLower (List<String> con nomi in lowercase per ricerca veloce)
    - Fallback: se il file non esiste o è malformato, log errore e
      inizializza liste vuote (List.of())

  Metodo search(query):
    - Input: stringa di ricerca (query param "search")
    - Output: List<ComuneDto> (max 10 risultati)
    - Logica:
      1. Se query vuota/null -> List.of()
      2. Normalizza query in lowercase
      3. Prima passata: risultati che iniziano con la query (startsWith)
      4. Seconda passata (se < 10 risultati): risultati che contengono
         la query ma non iniziano con essa (contains)
    - Non usa API esterne: dati completamente offline da JSON statico

DTO: comuni/dto/ComuneDto.java
  - nome: String (nome del comune)
  - provincia: String (sigla provincia, 2 caratteri, es. RM)
  - codiceCatastale: String (codice catastale, 4 caratteri, es. H501)

Controller: comuni/controller/ComuniController.java
  Endpoint: GET /api/v1/comuni?search=...
  Accesso: Pubblico (permitAll in SecurityConfig)
  Risposta: 200 OK, array di ComuneDto
    [{"nome":"Roma","provincia":"RM","codiceCatastale":"H501"}, ...]
  Nessuna autenticazione richiesta.

8.2 Integrazione Photon (Frontend)

File: pages/auth/register.component.ts
  API esterna: Photon (https://photon.komoot.io) — geocoding open-source
    basato su OpenStreetMap.

  Interfacce TypeScript:
    PhotonProperties { street?, name?, housenumber?, postcode?, city?, country? }
    PhotonFeature { properties: PhotonProperties }
    AddressSuggestion { street, housenumber, postcode, city, country }
    ComuneDto { nome, provincia, codiceCatastale }

  Flusso Ricerca Luogo di Nascita (Comuni):
    1. Utente digita in birthPlaceSearch (input field)
    2. onCitySearchInput(): debounce 100ms (setTimeout/clearTimeout)
    3. Chiamata GET http://localhost:8081/api/v1/comuni?search=<query>
    4. Risultati mostrati in dropdown autocomplete
    5. selectCity(city): setta birthPlace, birthProvince, birthCatatalCode
    6. Aggiorna birthPlaceSearch con formato "Nome (PR)"
    7. Click fuori dal wrapper -> chiude dropdown (@HostListener)

  Flusso Ricerca Residenza (Photon):
    1. Utente digita in residenceSearch (input field)
    2. onResidenceSearchInput(): attivata solo se >= 2 caratteri
    3. Chiamata fetch() a https://photon.komoot.io/api/?q=<query>&limit=5&countrycode=IT
    4. Parsing risposta JSON: estrae features[].properties
    5. Mappa in AddressSuggestion[]: street, housenumber, postcode, city, country
    6. selectAddress(addr): setta residence, houseNumber, postcode
    7. Fallback: se fetch fallisce (rete assente, API down) -> filteredAddresses = []
       -> dropdown nascosto, nessun messaggio errore all'utente
    8. Click fuori -> chiude dropdown

  Differenze tra i due servizi:
    - Comuni: backend Java, dati statici da JSON, risposta immediata,
      include codiceCatastale per generazione Codice Fiscale
    - Photon: API esterna (komoot.io), geocoding su OSM, include
      street/housenumber/postcode, dipendente da connessione internet

8.3 Autocompletamento Codice Fiscale (Frontend)

  File: pages/auth/register.component.ts (metodo generateFiscalCode + computeFiscalCode)
  Implementazione client-side del calcolo del Codice Fiscale italiano:
    - surnameCode(name): consonanti + vocali del cognome, max 3 caratteri
    - nameCode(name): se 4+ consonanti -> prima+terza+quarta, altrimenti standard
    - birthYearCode(date): ultime 2 cifre dell'anno
    - birthMonthCode(date): lettera A=Gen, B=Feb, C=Mar, D=Ape, E=Mag,
      H=Giu, L=Lug, M=Ago, P=Set, R=Ott, S=Nov, T=Dic
    - birthDayGenderCode(date): giorno; se F -> giorno+40
    - computeCIN(partial): carattere di controllo su 15 caratteri
      (mappe oddMap/evenMap da tabelle ministeriali)
  Validazione: lunghezza 16 caratteri, solo uppercase

8.4 Gestione Errori e Fallback

  Comuni (backend):
    - File JSON non trovato -> log error, liste vuote, search() restituisce []
    - Query senza risultati -> array vuoto (200 OK)
    - Nessuna dipendenza da servizi esterni

  Photon (frontend):
    - Errore di rete o API down -> filteredAddresses = [], dropdown nascosto
    - Nessun messaggio di errore visibile all'utente (fallback silenzioso)
    - Utente può comunque inserire manualmente la residenza

9.2 Generazione PDF Estratto Conto (Cliente)

  File: pages/customer/customer-profile.component.ts
  Metodo: generatePdf()
  Trigger: Pulsante "Scarica PDF" nella modale di selezione conto

  Flusso:
    1. isGeneratingPdf.set(true) -> mostra spinner
    2. Legge profilo utente e transazioni filtrate per conto selezionato
    3. Crea nuovo documento jsPDF (formato A4 verticale)
    4. HEADER:
       - Nome banca (bold, size 20, colore scuro) a y=22
       - Titolo "Estratto Conto" (normal, size 10, grigio) a y=30
       - Data generazione a y=36
       - Intestatario conto, Codice Fiscale, Email (size 12) a y=46-58
    5. TABELLA TRANSAZIONI (autoTable):
       - Colonne: Data, Descrizione, Importo, Stato
       - Header: fillColor [10,25,47], textColor oro [229,169,60]
       - Righe alternate: fillColor [245,247,250]
       - Importi: segno + per DEPOSIT, - per gli altri
       - startY dinamico: 66 se profilo presente, 40 se assente
    6. FOOTER (per ogni pagina):
       - Numerazione "Pagina X di Y" centrata in basso
       - Font size 8, colore grigio
    7. Salvataggio: doc.save("estratto_conto_YYYY-MM-DD.pdf")
    8. isGeneratingPdf.set(false), chiude modale

  Dati inclusi:
    - Tutte le transazioni del conto (filtrabili per conto specifico)
    - Campi: createdAt, description, typeName, amount, statusName
    - Formattazione: CurrencyPipe (EUR), DatePipe (locale utente)
